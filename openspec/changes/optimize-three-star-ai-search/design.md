## Context

当前 `doublethree` 将棋盘状态、启发式评分、落子、禁手判断和多组递归战术函数集中在同一对象中。三星入口 `harsh_analysisboard` 先执行立即胜负及强制攻防规则，再遍历边界内空点进行评分。深层搜索已具备冲四、双三和连续强攻的雏形，但存在候选过早截断、方向过滤与坐标错误，并依赖全局 `rand()` 在评分和防守选择中注入噪声。`modelB` 和训练计数字段没有形成可运行的参数实验或自对弈流程。

用户对局需要保留变化感，但离线比较必须复现同一结果。优化还必须兼顾旧设备上的响应时间，并能将新旧三星各执一方的 200 局最终对抗结果写成 Markdown 报告。

## Goals / Non-Goals

**Goals:**

- 恢复搜索方向、边界、坐标、候选集合和棋局状态的正确性，并用战术回归测试锁定行为。
- 在固定预算内增加三星对高价值连续威胁的有效搜索深度，而不是均匀扩展所有空位。
- 让用户模式在不主动选择明显劣着、不漏掉必胜或必要防守的前提下产生多样落子。
- 将所有搜索及随机参数集中成可命名配置，支持内部参数组的自动对抗筛选。
- 保留可独立调用的旧三星基线，并完成新算法执黑 100 局、执白 100 局的最终盲测报告。

**Non-Goals:**

- 不引入神经网络、在线学习、联网服务或第三方棋力引擎。
- 不改变一星、二星的产品定位，也不重做现有 iPhone/iPad 界面。
- 不以完全求解 15×15 五子棋或无限搜索作为目标。
- 不保证每个局面都产生不同落子；只有存在多个安全近优候选时才提供随机性。

## Decisions

### 1. 先建立可测试的引擎边界，再调整搜索深度

把“分析局面并返回落子”与 UI、真实落子提交分开。分析输入包含棋盘、行棋方、禁手规则、参数配置、运行模式和随机种子；输出包含选择点、候选信息、战术等级和搜索统计。搜索期间使用成对的 make/unmake 或可靠的棋盘快照，保证每次分析结束后输入局面不变。

旧三星逻辑以测试专用的 `legacy-three-star` 配置/实现固定下来，不随新算法修复而变化。若为了注入独立随机源而提取公共接口，必须通过黄金局面测试证明固定种子下仍重现基线行为。

选择这一方式而不是继续直接修改 `harsh_analysisboard`，是为了让新旧引擎能够在同一进程内安全对弈并获得逐步统计。

### 2. 使用战术分层候选和预算化迭代加深

候选按下列优先级生成并去重：

1. 立即获胜；
2. 阻止对手立即获胜；
3. 已证明的连续冲四、四三、双三等强制进攻；
4. 阻断对方高强度强制路径；
5. 距已有棋子限定邻域内的普通候选。

不可遗漏的战术层扫描完整合法集合；普通层才按确定性启发式排序截取 Top-K。三星使用迭代加深，使完整完成的上一层结果始终可用，并通过最大深度、节点数和可选墙钟时间共同限制搜索。初始实验组以现有约 8/8/10 的路径上限为基线，比较 10/10/12、12/12/14 等配置，但最终值由独立调参赛决定，而不是在设计中硬编码。

增加棋盘哈希置换表，键至少包含棋盘、行棋方、禁手模式、搜索类型和剩余深度；仅复用与当前配置版本相容的结果。相比直接把所有递归上限提高，这能把计算集中在可改变胜负的分支。

### 3. 使用“战术门控 + 近优集合 + Softmax”的受控随机策略

随机性不再直接加到每个候选的原始评分中。流程为：

```text
完整确定性分析
       │
       ├─ 必胜 / 唯一必要防守 / 唯一已证明最优 ──▶ 确定性落子
       │
       └─ 多个安全候选
              │
              ├─ 剔除导致对手立即胜或进入已证明败势的点
              ├─ 保留 Top-K 且与最佳分差不超过阈值的近优集合
              └─ 按 exp((score-best)/temperature) 带权抽样
```

随机温度随局面阶段和候选分差调整：开局/平稳局面允许更高多样性，战术尖锐或优势差明显时温度降低。候选数不足两个时不抽样。候选顺序在抽样前使用稳定坐标排序，避免遍历顺序成为隐式偏差。

用户模式每盘创建独立 PRNG 上下文，以系统随机值和新棋局标识派生种子；不会调用共享全局 `srand/rand`。评测和单元测试模式必须显式传入种子，相同局面、配置和种子产生相同落子及统计。选择 Softmax 而不是均匀随机，是因为它能保留“越强的候选越常出现”的关系；选择近优门控而不是评分噪声，是为了避免随机量覆盖必要防守或战术结论。

### 4. 参数配置和内部 AB 调优分离于最终验收赛

定义命名的 `AIProfile`，至少包含：各战术搜索深度、普通候选 Top-K、节点/时间预算、置换表容量、评估权重、近优分差、随机温度、最大随机候选数和配置版本。旧三星、新三星候选组以及最终三星均使用不可变快照记录。

内部调参赛使用训练种子集，通过逐轮淘汰比较正确性修复、深度、宽度、权重和随机参数；结果至少记录胜和负、分先后手得分率、每步 p50/p95 用时和节点数。最终 200 局使用未参与调参的保留种子，防止针对验收局过拟合。

### 5. 最终报告采用严格的分先后手配对赛

准备 100 个合法且未提前形成胜负的保留开局/种子。每个开局进行两盘，交换新旧引擎颜色：

- 新三星执黑、旧三星执白：100 局；
- 新三星执白、旧三星执黑：100 局。

两盘共享相同开局标识，双方各自使用独立但可由比赛种子推导的 PRNG 流，避免调用顺序互相污染。规则、禁手设置、搜索预算和终局判定必须写入报告。异常、超时、非法着和达到最大手数的处理规则在比赛开始前固定，不得静默丢弃；若发生，应单独计数并保留棋谱。

报告文件名包含 UTC 时间和新旧配置版本，写入 `/Users/wangzicheng/Downloads/logs_five_chess`。报告至少包含运行环境、提交版本、参数快照、总体及分颜色胜和负、得分率、Wilson 95% 置信区间、耗时/节点分位数、随机性与复现命令、异常列表和代表棋局。原始逐局结果以机器可读文件随报告保存，Markdown 中引用其文件名和校验值。

## Risks / Trade-offs

- [加深搜索造成用户等待时间变长] → 使用迭代加深、候选裁剪、置换表和明确预算，并在报告中检查 p95 每步耗时。
- [候选裁剪漏掉安静但关键的防守] → 战术候选不受普通 Top-K 裁剪，增加已知杀棋、防杀和旋转/镜像回归局面。
- [随机性降低三星棋力] → 随机仅作用于通过战术安全检查的近优集合，内部调参和最终基准都分颜色验证。
- [时间预算导致跨设备不完全复现] → 正式强度赛以节点预算作为主要终止条件，墙钟预算只作安全上限；报告记录硬件和超时。
- [旧算法使用共享全局随机数，污染公平性] → 为每个引擎提供独立随机上下文，并以黄金测试锁定旧基线的固定种子序列。
- [200 局统计能力有限] → 同时报告点估计和置信区间，不把细小胜率差描述为确定提升；保留原始数据以便追加比赛。
- [报告目录位于仓库沙箱之外] → 实施阶段先创建仓库内的报告及原始结果，再在获得授权后复制到目标目录并校验一致性。

## Migration Plan

1. 建立旧三星基线、引擎调用边界、固定种子及黄金测试。
2. 修复正确性问题并通过战术、边界、旋转和镜像测试。
3. 引入新搜索与受控随机参数，运行内部训练种子 AB 赛选择最终配置。
4. 保持 UI 的三星索引不变，将其切换到最终配置；一星、二星继续使用现有入口。
5. 在保留种子上运行最终 200 局并生成报告。若出现非法着、状态污染或无法解释的棋谱差异，验收赛作废并在修复后从头重跑。
6. 回滚时将三星入口恢复到 `legacy-three-star`，保留测试工具和报告数据用于诊断。

## Open Questions

- 最终用户模式的思考时间上限需要通过真机测量确定；首轮实现先以节点预算为主，并记录不同设备数据。
- 正式报告默认采用当前应用实际启用的禁手设置；若产品希望同时公布有禁手和无禁手成绩，可在同一框架追加独立赛段，但不计入本次规定的 200 局。
